# VALIDATION_EVIDENCE.md

**Project:** Intent Core Alignment System
**Purpose:** A concise, evidence-typed record of what has been validated, how, and with what limitations.
**Companion document:** `docs/IMPLEMENTATION_STATUS_AND_ROADMAP.md` §E covers the same manual validations in narrative form; this document is the structured table.

## Evidence types

- **Automated test** — a passing test in this repository's committed test suite. Reproducible by running `pytest` (`apps/api`) or `vitest run` (`apps/web`).
- **Repository evidence** — provable by inspecting committed code, migrations, or Git history directly.
- **Manual owner-supplied execution** — reported by the project owner as having been run against a real external system (real ftrack workspace, real DeepSeek API), or against a real locally-running process (a real `uvicorn` server, real HTTP requests, no `TestClient`) exercised outside the automated `pytest`/`vitest` suite. Not reproducible from the repository alone merely by re-running the test suite — it requires actually starting the described process(es) again; this project's own testing rules deliberately keep real external calls, and full real-process HTTP walkthroughs, out of the automated suite.

No API keys, credentials, full environment-variable values, or other sensitive account details appear anywhere in this document.

## Known non-blocking observations (Step 1A)

Observed during the Step 1A-Backend and Step 1A-UI validation passes above. None is a newly discovered product defect; all are recorded as observed, intentional prototype behaviour.

**A. Extra input fields (Step 1A-Backend).** Client-supplied fields such as `id`, `order_index`, `created_at`, and `created_by_actor_id` on a semantic-item input are currently *ignored* by the Pydantic input schemas rather than rejected. The server still generates its own UUID, derives `order_index` from array position, stamps its own `created_at`, and never accepts client-supplied provenance as authoritative. This is observed input-contract behaviour, not blocking for this prototype slice.

**B. SQLite `created_at` representation (Step 1A-Backend).** During the isolated-SQLite acceptance pass, `created_at` values were serialized without an explicit UTC offset. This was also observed on pre-existing `Project`/`Shot` objects (not introduced by migration `0014`), and is a known `DateTime(timezone=True)` round-trip characteristic of the SQLite dialect specifically (see migration `0010`'s own handling of a related PostgreSQL-timestamp issue). The production PostgreSQL path remains the intended source of truth for timezone-aware behaviour.

**C. Actor-id role-switch prototype behaviour (Step 1A-UI).** Role defaults are `vfx_supervisor` → `vfx-1`, `cg_supervisor` → `cg-1`, `artist` → `artist-1`. When Role changes, an untouched/default Actor id updates to the new role's default; a manually entered custom Actor id is preserved across Role changes within the same mounted page session. A full browser refresh remounts the page and restores the current role's default Actor id — no identity persistence, authentication, `localStorage`, or URL state was added. This is intentional prototype interaction behaviour, not a persistent identity system, and is not a defect.
