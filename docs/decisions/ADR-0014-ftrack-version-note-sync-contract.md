# ADR-0014: ftrack Version / ReviewNote sync contract

## Context

`docs/step-8/01_STEP_8A_FTRACK_VERSION_NOTE_RELATIONSHIP_VALIDATION.md` validated the real ftrack `AssetVersion`/`Note` relationship shapes against the controlled trial workspace and proposed a minimum sync contract. Step 8B (`docs/step-8/02_STEP_8B_VERSION_NOTE_SYNC_CONTRACT.md`) re-examined that proposal against additional real-workspace evidence and the actual current CG/Artist page code, and revised it on two material points before locking it. This ADR records the durable architectural decisions from that process — the shared domain schema, Agent/API contract, and write-boundary changes `CLAUDE.md`'s change-boundary list requires a Decision Record for — not the investigation narrative itself (see the two documents above for that).

Four decisions needed to be made and recorded before Step 8C can implement anything:

1. Does `Version` gain a persisted Task relationship, or stay Shot-only?
2. What do `Version.created_at`/`ReviewNote.created_at` mean for a synced row, and how is a non-ICAS author represented?
3. Where does ftrack identity (`source="ftrack"` + `external_id`) enter the system for `Version`/`ReviewNote` — the existing public create contract, or somewhere new?
4. What reconciliation strategy discovers and re-syncs changes, given no real ftrack modification timestamp exists?

## Decision

### 1. `Version` gains a nullable `task_id` FK; `ReviewNote` gains no new relational target

`Version.task_id` (nullable FK to `tasks.id`) is added. `ReviewNote` continues to relate only to `Version` (`version_id`, unchanged hard FK).

This reverses Step 8A's original recommendation ("no persisted `Version.task_id` is required"). The reversal is evidence-driven, not stylistic: a real Shot in the controlled workspace (`bc0040`) has `AssetVersion`s from three distinct real ftrack Tasks (Compositing, Rotoscoping, Layout), and the two existing pages that would consume synced Versions per-Task — CG's Version Review page and Artist's Current Version page — both currently call `listVersionsForShot(shot_id)` with no Task filter at all. Shot-only storage would make those pages show every Task's Versions inside every other Task's workspace, a real cross-Task data leak once real multi-Task Shots are synced, not a hypothetical one.

The FK is nullable specifically so every existing manually-created `Version` row (which has never had Task identity, by an existing, deliberate, documented product decision — see `versions_and_feedback/models.py`'s own module docstring) is left completely untouched. `CrossRoleAssessment` already works around `Version`'s lack of Task identity by requiring the caller to supply `task_id` explicitly at generation time; this ADR does not change that pattern, it gives ftrack-sourced Versions a structurally reliable Task identity so a future caller (or page) does not have to guess or re-derive it.

### 2. `created_at` keeps ICAS-ingestion-time meaning; new `source_created_at` and `external_author_*` fields are added, kept structurally separate from human-actor identity

`Version.created_at`/`ReviewNote.created_at` are **not** redefined for synced rows — they continue to mean "when this row was written into ICAS," exactly as every existing consumer of those columns (ordering in `list_versions_for_shot`, VFX/Artist page sort order) already assumes. A new nullable `source_created_at` column (on both tables) holds the real ftrack `AssetVersion.date`/`Note.date` value as a separate fact. No `source_updated_at` is added, because real, exhaustive schema inspection of the live ftrack server found no modification-timestamp field of any kind on either entity type — only `date` exists on both.

New nullable `external_author_id`/`external_author_name` columns hold the real ftrack author as pure provenance metadata, sourced from two structurally distinct real fields: `external_author_id` is always the real ftrack stable account id (`AssetVersion.user.id` / `Note.author.id`) — **never** `username`, email, or a display name, confirmed by targeted real-workspace queries to be populated in every case the `user`/`author` relation exists at all (99/99 `AssetVersion`s; 45/45 direct-Note authors; 33/33 non-null `review_session_object`-Note authors, including a specifically checked guest/client reviewer whose `username` was already known missing — their `author.id` was present regardless). `external_author_id` is `null` only when the source row's `author`/`user` relation is itself entirely absent, which real data shows happens for roughly two-thirds of `review_session_object`-parented Notes (60/93) but never for `AssetVersion.user` or a direct Note's `author`. `external_author_name` is the separate, genuinely-optional display fallback (`username`, else first/last name). `created_by_actor_kind`/`created_by_actor_id`/`created_by_human_role` for a synced row are fixed to `"system"` / `"ftrack-sync"` / `None`, always — never derived from the ftrack author, and never given a `human_role`. This is a direct enforcement of the stated authority rule: an ftrack author is production provenance, never automatically a Human VFX Supervisor, Human CG Supervisor, or Human Artist in ICAS. `ActorContext`'s own invariant (a `"human"` actor must carry a `human_role`; nothing else may) makes it structurally impossible to represent an ftrack author as a human actor without violating that rule, which is additional, independent confirmation this is the only workable shape, not just the chosen one.

### 3. ftrack identity for Version/ReviewNote enters only through a new, separately-authenticated internal sync boundary — not the existing public create contract

`VersionCreate`/`ReviewNoteCreate` are not extended with `source`/`external_id`. A new, distinct contract and endpoint pair (`VersionSyncCreate`/`ReviewNoteSyncCreate` via `POST /internal/sync/versions`/`POST /internal/sync/review-notes`) is the only path by which `source="ftrack"` data enters `Version`/`ReviewNote`, and it additionally requires a shared internal-service token header that the existing `POST /projects`/`/shots`/`/tasks` endpoints do not require.

This is a deliberate divergence from the existing Project/Shot/Task precedent, not an oversight of it. Inspection of `production_context/router.py` found that `create_project`/`create_shot`/`create_task` already accept `source="ftrack"` + an arbitrary `external_id` through their ordinary public create endpoints with **no actor dependency and no role check of any kind** — any network client can already inject a fake Project/Shot/Task claiming ftrack provenance today. Extending `Version`/`ReviewNote` the same way would compound rather than fix that gap, and the consequence is materially worse here: `Version`/`ReviewNote` feed `AlignmentAssessment`/`CrossRoleAssessment`, ICAS's AI-assisted evaluation of creative alignment, so fabricated "production evidence" could pollute an assessment a Human Supervisor later relies on. The existing Project/Shot/Task gap is named in the Step 8B document as a real, live risk but is explicitly not remediated by this ADR — retrofitting an existing public contract's authentication behavior is itself a change to a public API contract under `CLAUDE.md`'s change-boundary list and needs its own separate sign-off.

A repeat sync of an already-linked `external_id` is a true no-op, not an update — also a deliberate divergence from Project/Shot/Task (which do support field updates on repeat sync). `Version`/`ReviewNote` are documented immutable, append-only, with no update endpoint anywhere in the API surface; a sync path that mutated them on every re-run would contradict that existing product rule. The direct consequence — a `Note` edited in ftrack after first sync is never reflected in ICAS — is accepted and named explicitly as a permanent limitation, not hidden as an implementation detail, because no real signal exists to detect such an edit in the first place (see Decision 4).

### 4. Reconciliation is a complete per-linked-Shot sweep on every run; no Version/Note `SyncCursor` is created

Every reconciliation run repeats a complete, unbounded targeted query (`AssetVersion where asset.parent.id is <shot_id>`, plus the direct- and `ReviewSessionObject`-mediated Note queries) for every already-linked Shot — scoped by "already-linked Shots" (a small, controlled set), not by any timestamp. **No `SyncCursor` row is created for this sync.** An earlier draft of this ADR and the Step 8B document proposed two placeholder cursors (`"ftrack_version_reconciliation"`, `"ftrack_note_reconciliation"`) that nothing in the strategy actually consulted to decide what to examine — unused scaffolding, not a real optimization — and both are removed rather than kept as inert placeholders. The existing `"ftrack_shot_reconciliation"` cursor (Project/Shot/Task reconciliation, ADR-0011) is untouched.

This was chosen over pure timestamp-incremental polling because real, exhaustive schema inspection confirmed there is no modification timestamp on `AssetVersion` or `Note` — a cursor-only design could under-cover a Shot's real history on first link (a newly-linked Shot can already have years of real AssetVersions/Notes) and has no way to distinguish "nothing changed" from "the cursor missed something," since there is no field to sanity-check it against. The full per-Shot re-sweep is not sensitive to this gap at all — it re-derives the complete real relationship graph every time, at a real, measured cost (Step 8A: an equivalent query returns in well under a second for one Shot). No cursor is needed to make this safe or idempotent either: exact `ExternalEntityLink` identity (`find_linked_entity_id`) already makes re-examining an already-synced row a true no-op, so a cursor's only possible value here would be *skipping ftrack re-querying* at larger scale — a genuine but explicitly deferred production-scale optimization, not something correctness depends on today. This directly satisfies the given instruction to prefer correctness and idempotency over production-scale optimization for a prototype, and to avoid building cursor machinery that does not actually control the sync.

The same investigation also produced an exact, workspace-real number for how often the `ReviewSessionObject`-mediated Note path will actually resolve: only 8 of 68 distinct `ReviewSessionObject` ids referenced by real Notes still exist in the workspace (the other 60 have been deleted — a normal ftrack review-session cleanup pattern, not a bug). The reconciliation logic must treat this as the expected steady-state outcome (skip and log, at a high, named rate) rather than as an anomaly to alert on per occurrence.

## Alternatives considered

- **Shot-only `Version` storage** (Step 8A's original proposal). Rejected — see Decision 1; disproven by real multi-Task-per-Shot data and the current CG/Artist page code, not merely reconsidered on principle.
- **A denormalised Task name/display field instead of a `task_id` FK.** Rejected — the task brief's own constraint against name-based identity matching rules this out as the filtering key; ftrack Task names are not guaranteed stable, and CG/Artist pages need a reliable join, not a display convenience.
- **Redefining `created_at` to mean external ftrack event time for synced rows.** Rejected — would silently change an already-depended-upon column's meaning for a subset of rows, breaking existing ordering logic in `list_versions_for_shot` and multiple frontend sort call sites, none of which distinguish row provenance today.
- **Extending the existing public `VersionCreate`/`ReviewNoteCreate` contracts with `source`/`external_id`**, mirroring Project/Shot/Task exactly. Rejected — would replicate an already-real, already-unauthenticated spoofing surface onto two entities with materially higher downstream trust consequences (AI-assisted alignment evaluation).
- **Pure timestamp-incremental reconciliation** (`AssetVersion.date`/`Note.date` after cursor only, no full re-sweep). Rejected for this prototype — the explicit instruction to avoid a cursor strategy that risks silently missing content, combined with the now-confirmed total absence of any modification timestamp, means a cursor-only design has no self-check; a scope-bounded full re-sweep does not share that weakness at prototype scale.
- **A full, unbounded workspace-wide re-sweep every run (not scoped to already-linked Shots).** Rejected — unbounded in the wrong dimension; scoping to already-linked Shots (a small, controlled set) is what keeps "prefer correctness" affordable, and auto-discovering new Shots via this path is explicitly out of scope (that remains Project/Shot/Task reconciliation's job).
- **Two placeholder `SyncCursor` rows for Version/Note sync** (`"ftrack_version_reconciliation"`, `"ftrack_note_reconciliation"`), present in an earlier draft of this ADR as a "forward-compatibility" gesture toward a future optimization. Rejected and removed — nothing in the selected reconciliation strategy ever reads them to decide what to examine, so they would be unused scaffolding from the moment they were created; a real cursor-based optimization, if and when production scale demands one, is a new decision to make with its own evidence at that time, not something to half-build now.
- **Allowing controlled mutation of a synced `ReviewNote`/`Version` on re-sync**, to at least partially track content edits. Rejected — would contradict the existing, independently-decided product rule that these rows are immutable/append-only; solving "detect a ftrack content edit" properly requires a real modification signal ftrack does not currently expose, not a workaround that weakens an unrelated existing guarantee.
- **Using `username`/email/display name as `external_author_id`.** Rejected — real, exhaustive data shows a stable `user.id`/`author.id` is reliably present whenever the author relation exists at all (99/99 `AssetVersion`s, 45/45 direct-Note authors, 33/33 non-null `review_session_object`-Note authors), including for guest/client reviewers whose `username` is unset; substituting a mutable username for a stable id would be strictly worse identity, not a necessary fallback.

## Consequences

- `Version` gains **four** new additive, nullable columns: `task_id`, `source_created_at`, `external_author_id`, `external_author_name`. `ReviewNote` gains **three**: `source_created_at`, `external_author_id`, `external_author_name` (no `task_id` — a Note has no Task identity of its own). `source` already exists on both tables today (`versions_and_feedback/models.py`) and is not a new column; only its value-setting path changes (hardcoded `"ftrack"` server-side for synced rows, §8/Decision 3). All new columns are additive, no backfill, zero risk to existing rows, and a trivial rollback (column drop) if Step 8C needs to be reverted.
- `external_author_id` is always sourced from a real ftrack stable id field (`user.id`/`author.id`), never from `username`, email, or a display name — locked by real, exhaustive evidence, not assumption (Decision 2).
- CG's Version Review page and Artist's Current Version page must be updated in Step 8C to filter by `task_id` when present (falling back to today's full-Shot-list behavior for `task_id IS NULL` legacy/manual rows) — a real, necessary consequence of Decision 1, not optional polish.
- Any page displaying ftrack-origin `Version`/`ReviewNote` rows chronologically should sort by `COALESCE(source_created_at, created_at)`, not `created_at` alone, once a historical backfill sync can insert years of real history in one run — a real consequence of Decision 2 that Step 8C's page-integration slice must account for.
- A second, stricter authentication boundary (an internal shared-secret token) now exists in the API surface, distinct from and stronger than the existing Project/Shot/Task endpoints' complete lack of caller verification — a visible inconsistency until a follow-up ADR closes the Project/Shot/Task gap, named here so it is not mistaken for an oversight.
- ftrack-authored Note/Version content synced into ICAS is permanently frozen at first-sync state; a ftrack-side edit after that point is invisible to ICAS unless a future ADR revisits this once a real modification signal becomes available (e.g. Event Hub).
- Step 8C's reconciliation job re-derives each linked Shot's full AssetVersion/Note graph on every run and creates **no `SyncCursor` row of any kind** for Version/Note sync; the existing Project/Shot/Task cursor is unaffected. This is intentionally not optimized for scale yet — a future cursor-based optimization is a new, separate, evidence-driven decision for a later ADR to make, not something pre-built here.
